## Цель недели {#tsel-nedeli}

Проверить готовность на новых задачах, найти повторяющиеся ошибки и составить конкретный план дальнейшей подготовки.

После недели нужно уметь:

- оценивать прогресс по наблюдаемым данным;
- отличать случайную ошибку от системной;
- находить этап решения, на котором возникает проблема;
- выбирать упражнение под конкретный пробел;
- проводить финальный mock без изменения условий;
- принимать решение о переходе к реальным интервью;
- составлять план поддержки навыка после роадмапа.

## Диагностика — не новый экзамен по всем темам {#diagnostika-ne-novyy-ekzamen-po-vsem-temam}

Цель не в том, чтобы за семь дней повторить весь курс.

Нужно ответить на вопросы:

1. Какие навыки уже стабильны?
2. Какие ошибки повторяются?
3. На каком этапе решения они возникают?
4. Какие ошибки блокируют результат?
5. Что можно исправить короткой практикой?
6. Что требует возврата к отдельной теме?

Повторение выбирается по данным из Mixed Problems и Mock Interviews, а не по ощущению «я плохо знаю всё».

## Входные данные диагностики {#vkhodnye-dannye-diagnostiki}

Собери результаты последних `10–15` задач и двух mock-интервью:

- название задачи;
- уровень сложности;
- время до brute force;
- время до оптимальной идеи;
- время до рабочего кода;
- количество и уровень подсказок;
- найденные самостоятельно ошибки;
- корректность сложности;
- результат повторного решения.

Без этих данных легко повторять знакомые темы и игнорировать реальную проблему.

## Таблица попыток {#tablitsa-popytok}

Пример структуры:

| Задача | Идея | Код | Проверка | Подсказка | Повтор |
| --- | --- | --- | --- | --- | --- |
| A | Самостоятельно | Ошибка границы | Исправил сам | Нет | Успешно |
| B | После сигнала | Корректно | Слабые тесты | Уровень 1 | Еще не было |
| C | Самостоятельно | Корректно | Корректно | Нет | Успешно |

Таблица нужна для поиска повторов, а не для красивой статистики.

## Уровни самостоятельности {#urovni-samostoyatelnosti}

Разделяй результаты:

| Уровень | Что произошло |
| --- | --- |
| 0 | Решение просмотрено полностью |
| 1 | Потребовался переход или псевдокод |
| 2 | Потребовалось название структуры или паттерна |
| 3 | Идея найдена самостоятельно, были ошибки кода |
| 4 | Полностью самостоятельное решение и проверка |

Задача, решенная сразу после просмотра, не подтверждает навык. Главный показатель — повторное решение через несколько дней без старого кода.

## Случайная и системная ошибка {#sluchaynaya-i-sistemnaya-oshibka}

Ошибка считается кандидатом на системную, если:

- повторилась в двух или более задачах;
- появляется в разных паттернах;
- не обнаруживается собственными тестами;
- уже обсуждалась, но снова возникла;
- приводит к неверной идее или незавершенному коду.

Одна опечатка, самостоятельно найденная при trace, не требует возвращения к целому этапу.

## Пять уровней проблемы {#pyat-urovney-problemy}

## 1. Понимание условия {#1-ponimanie-usloviya}

Симптомы:

- решается другая задача;
- путается подстрока и подпоследовательность;
- игнорируется порядок ответа;
- используются несуществующие гарантии.

Действие:

- переформулировать условие своими словами;
- выписать вход и выход;
- построить собственный пример;
- перечислить допущения до кода.

## 2. Распознавание подхода {#2-raspoznavanie-podkhoda}

Симптомы:

- brute force есть, но повторяющаяся работа не замечена;
- паттерн становится очевидным только после названия;
- выбирается привычная структура независимо от операций.

Действие:

- решить три смешанные задачи с одинаковым скрытым сигналом;
- после brute force явно выписывать повторную операцию;
- сравнивать две возможные структуры и их стоимость.

## 3. Алгоритмический переход {#3-algoritmicheskiy-perekhod}

Симптомы:

- структура выбрана правильно, но инвариант неверен;
- DP-состояние нельзя объяснить;
- окно сжимается по неправильному условию;
- DFS возвращает не ту информацию родителю.

Действие:

- заполнить состояние вручную;
- нарисовать таблицу или дерево вызовов;
- построить минимальный контрпример;
- записать переход словами до формулы.

## 4. Реализация {#4-realizatsiya}

Симптомы:

- ошибки `left <= right` и `left < right`;
- неверный индекс `i` или `i - 1`;
- потеря ссылки Linked List;
- поздний `visited`;
- неправильный порядок обновления DP.

Действие:

- реализовать шаблон с чистого листа три раза;
- использовать минимальные входы;
- вести таблицу значений после каждой строки;
- отдельно проверять порядок обновления переменных.

## 5. Проверка и коммуникация {#5-proverka-i-kommunikatsiya}

Симптомы:

- ошибка остается незамеченной;
- тестируется только основной пример;
- сложность называется без объяснения;
- во время паузы кандидат молчит.

Действие:

- составлять тесты до запуска;
- проговаривать инвариант после каждой логической части;
- записывать устное объяснение;
- проверять код построчно как интерпретатор.

## Матрица слабых мест {#matritsa-slabykh-mest}

| Наблюдение | Вероятная причина | Точечное упражнение |
| --- | --- | --- |
| Не узнаю окно | Не выделяю непрерывный диапазон | 3 смешанные задачи на диапазон |
| Ошибки Binary Search | Нет инварианта границ | Таблица `left`, `middle`, `right` |
| DFS зацикливается | Поздний `visited` | 2 графа с циклом вручную |
| Теряю узлы списка | Меняю ссылку до сохранения | 3 ручных разворота |
| DP не начинается | Не определено состояние | Письменно ответить на 5 вопросов |
| DP дает повторный выбор | Неверный порядок обхода | Сравнить циклы Knapsack |
| Не нахожу greedy | Нет доказательства выбора | Контрпример + exchange argument |
| Код верен, но медленный | Пропущена скрытая операция | Посчитать стоимость каждой строки |
| Не нахожу ошибку | Нет граничных тестов | 5 тестов до запуска |
| Не успеваю | Слишком рано пишу код | Таймер по этапам решения |

## Как выбрать приоритет исправления {#kak-vybrat-prioritet-ispravleniya}

Для каждой проблемы оцени:

- частоту;
- влияние на результат;
- стоимость исправления;
- вероятность встретить тему на целевых интервью.

Сначала исправляй частые блокирующие ошибки:

```text
неверный алгоритм > незавершенный код > граничная ошибка > стиль
```

Не трать основное время на косметику, если решение пока не проходит минимальные случаи.

## План точечного повторения {#plan-tochechnogo-povtoreniya}

Один блок исправления занимает `60–90` минут:

1. Прочитать только нужный раздел теории.
2. Вручную разобрать один пример.
3. Реализовать базовый шаблон без копирования.
4. Решить одну новую задачу.
5. Сделать trace до запуска.
6. Повторить задачу через день.

Если ошибка не повторилась, не нужно решать еще десять однотипных задач подряд.

## Пример диагностики {#primer-diagnostiki}

Предположим, результаты двух mock:

```text
Mock 1:
- правильный Sliding Window после подсказки уровня 1
- код готов за 38 минут
- left один раз сдвинулся назад

Mock 2:
- самостоятельно выбран Two Pointers
- код готов за 29 минут
- ошибка на пустом входе найдена при trace
```

Выводы:

- общая реализация циклов работает;
- проверка улучшилась;
- проблема сосредоточена в инварианте левой границы окна;
- повторять весь Two Pointers не требуется.

Следующее действие:

1. Письменно сформулировать инвариант Sliding Window.
2. Проследить `"abba"` и еще одну строку с повтором вне окна.
3. Решить новую задачу на динамическое окно.

## Финальные mock-интервью {#finalnye-mock-intervyu}

Проведи `2–3` интервью после точечного повторения.

Условия должны оставаться одинаковыми:

- `45–60` минут;
- неизвестная задача;
- без поиска;
- без запуска до ручной проверки;
- та же оценочная таблица;
- фиксация уровней подсказок.

Если между попытками меняются правила, сравнение результатов становится бессмысленным.

## Состав финальных задач {#sostav-finalnykh-zadach}

Выбери задачи из разных групп:

1. Массивы или строки с одним паттерном.
2. Tree, Graph или Grid.
3. Greedy или DP.

Не используй задачи, решения которых уже запомнены. Допустимо выбрать аналог знакомой задачи с измененным условием.

## Разобранный финальный пример {#razobrannyy-finalnyy-primer}

Задача: для каждого элемента вернуть произведение остальных без деления.

```text
[1, 2, 3, 4] -> [24, 12, 8, 6]
```

## Brute force {#brute-force}

Для каждого индекса перемножить все остальные числа.

- `n` позиций;
- до `n` умножений для каждой;
- время `O(n²)`.

Повторяющаяся работа: произведения слева и справа пересчитываются много раз.

## Оптимальная идея {#optimalnaya-ideya}

Для позиции `i` ответ равен:

```text
произведение слева от i * произведение справа от i
```

Сначала ответ заполняется левыми произведениями. Затем проход справа домножает правую часть.

```python
def product_except_self(numbers: list[int]) -> list[int]:
    result = [1] * len(numbers)

    left_product = 1

    for index, number in enumerate(numbers):
        # До обновления left_product содержит произведение
        # элементов строго слева от index.
        result[index] = left_product
        left_product *= number

    right_product = 1

    for index in range(len(numbers) - 1, -1, -1):
        # Домножаем на произведение элементов строго справа.
        result[index] *= right_product
        right_product *= numbers[index]

    return result
```

### Проверка на нулях {#proverka-na-nulyakh}

Для `[1, 0, 3]`:

```text
левые произведения:  [1, 1, 0]
после правого прохода: [0, 3, 0]
```

Алгоритм корректно работает с одним или несколькими нулями и не требует отдельных условий.

- Время: `O(n)`.
- Дополнительная память: `O(1)`, если список ответа не считается дополнительной памятью.

## Проверка кода перед запуском {#proverka-koda-pered-zapuskom}

Пройди чек-лист:

### Вход {#vkhod}

- Пустой вход.
- Один элемент.
- Минимальные и максимальные значения.
- Дубликаты.
- Нули и отрицательные числа.

### Циклы {#tsikly}

- Правильные начальная и конечная границы.
- Все указатели изменяются.
- Нет скрытого `O(n)` внутри цикла.
- Ответ обновляется в правильный момент.

### Структуры данных {#struktury-dannykh}

- `pop()` не вызывается у пустой структуры.
- `visited` обновляется вовремя.
- Индекс хранится, если нужен возраст или расстояние.
- Изменение входа разрешено условием.

### Рекурсия и DP {#rekursiya-i-dp}

- Есть базовый случай.
- Вход приближается к завершению.
- Состояние однозначно определено.
- Зависимости уже вычислены.
- Невозможное состояние отличается от нулевого ответа.

## Критерии готовности {#kriterii-gotovnosti}

Учебные ориентиры:

- не менее `80%` новых Easy решаются за `15–20` минут;
- около `50–60%` новых Medium по изученным темам решаются за `30–40` минут;
- подход объясняется до кода;
- brute force и оптимизация имеют корректную сложность;
- граничные тесты составляются самостоятельно;
- большая часть ошибок находится ручным trace;
- смешанные задачи решаются без названия паттерна;
- проведено минимум шесть mock-интервью за весь курс;
- в последних трех интервью нет одной повторяющейся критической ошибки.

Это ориентиры, а не гарантия найма. Конкретная компания может сильнее проверять Python, SQL, ML, системный дизайн или математику.

## Когда можно идти на реальные интервью {#kogda-mozhno-idti-na-realnye-intervyu}

Начинать реальные интервью можно до идеального результата, если:

- базовые структуры и сложности стабильны;
- есть рабочий процесс решения;
- ошибки обнаруживаются и исправляются;
- Medium иногда решаются самостоятельно;
- не возникает полного ступора без названия паттерна.

Реальные интервью тоже дают данные. Не обязательно откладывать их до стопроцентной готовности.

## Когда нужно вернуться назад {#kogda-nuzhno-vernutsya-nazad}

Вернись к конкретному этапу, если:

- не можешь реализовать базовую структуру;
- не понимаешь ее операции и сложность;
- три задачи одной темы требуют одинаковой подсказки;
- переход DP остается заученной формулой;
- обход графа регулярно зацикливается;
- Binary Search не имеет понятного инварианта.

Возвращайся к конкретной главе, а не начинай весь роадмап заново.

## План после 24-й недели {#plan-posle-24-y-nedeli}

Для поддержки навыка:

- две новые смешанные задачи в неделю;
- одно повторное решение старой сложной задачи;
- один mock каждые две недели;
- обновление журнала ошибок;
- точечное изучение требований целевых компаний.

Перед активным поиском работы частоту mock можно временно увеличить.

## Частые ошибки недели {#chastye-oshibki-nedeli}

1. Пытаться повторить весь курс одновременно.
2. Оценивать прогресс только количеством решенных задач.
3. Смешивать самостоятельное решение и решение после подсказки.
4. Считать любую опечатку системным пробелом.
5. Игнорировать повторяющуюся ошибку реализации.
6. Менять условия финальных mock.
7. Использовать запомненные задачи для высокой оценки.
8. Исправлять стиль до корректности алгоритма.
9. Начинать роадмап заново вместо точечного возврата.
10. Откладывать реальные интервью до недостижимого ощущения идеальной готовности.

## План недели {#plan-nedeli}

1. Собери данные последних задач и mock.
2. Раздели ошибки по пяти уровням.
3. Выбери две самые важные повторяющиеся проблемы.
4. Проведи точечные блоки исправления.
5. Выполни повторные решения через день.
6. Проведи `2–3` финальных mock.
7. Сравни результаты по неизменной таблице.
8. Составь план дальнейшей поддержки навыка.

## Задачи для самостоятельного решения {#zadachi-dlya-samostoyatelnogo-resheniya}

Выполняй как финальные mock-интервью.

### Задача 1. Course Schedule {#zadacha-1-course-schedule}

Дано количество курсов и пары `[course, prerequisite]`. Определи, можно ли закончить все курсы.

До кода:

- выбери направление ребер;
- объясни смысл цикла;
- выбери DFS с тремя состояниями или алгоритм Кана;
- назови сложность через `V` и `E`;
- подготовь пример с отдельной компонентой.

### Задача 2. Coin Change {#zadacha-2-coin-change}

Даны номиналы и сумма. Найди минимальное количество монет или верни `-1`.

До кода:

- объясни, почему greedy не работает для произвольных номиналов;
- сформулируй состояние;
- выбери значение невозможной суммы;
- укажи порядок заполнения;
- проверь сумму `0` и недостижимую сумму.
