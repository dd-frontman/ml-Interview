# Инструкции для Codex: ML Interview Workspace

## Цель проекта

Развивать русскоязычную базу знаний по Python, математике и Machine Learning для личного обучения, быстрого повторения и подготовки к работе ML Engineer. Сохранять существующую структуру VitePress, соглашения о контенте и проверки проекта.

## Обучение через примеры (Example-Driven Learning)

**При создании и существенном обновлении учебных материалов используй практико-ориентированное объяснение.** Предпочитай движение от понятной задачи к необходимой теории, а не длинную абстрактную теорию до первого примера.

Для каждой подходящей темы:

1. **Мотивация и задача.** В одном-двух абзацах объясни, зачем это нужно и какую конкретную проблему решаем.
2. **Минимальный работающий пример.** Покажи небольшой, воспроизводимый пример на Python или, для математической темы, простой числовой пример. Укажи ожидаемый результат и необходимые зависимости, если они есть.
3. **Теория на основе примера.** Последовательно объясни понятия, формулы и ключевые строки кода, связывая их с показанной задачей. Не пропускай важные предпосылки и ограничения.
4. **Усложнение.** По возможности добавь один реалистичный вариант или пограничный случай, который показывает, как принцип работает за пределами простого примера.
5. **Самостоятельная практика.** Предложи 1–3 задания от простого к сложному. Не раскрывай полное решение сразу, если материал рассчитан на самостоятельную работу; можно дать подсказку или вынести решение в отдельный раскрываемый раздел.
6. **Типичные ошибки.** Покажи распространённые заблуждения, баги и способы проверки результата.
7. **Краткое повторение.** Заверши компактными выводами и, когда уместно, подсказками о том, что полезно вспомнить перед собеседованием.

### Правила качества

- Примеры должны быть точными, исполняемыми и соответствовать изложенной теории. Не придумывай результаты экспериментов или метрики.
- Для ML-примеров по возможности фиксируй random seed, избегай утечки данных, разделяй обучение и оценку, объясняй выбор метрик и ограничения модели.
- Давай определения новых терминов простым русским языком, сохраняя общепринятые названия библиотек и технических понятий.
- Не превращай каждую заметку в огромный учебник: подбирай глубину по сложности темы. Для справочных страниц и коротких определений допускается сокращённая структура.
- Предпочитай небольшие самостоятельные примеры, которые можно проверить без тяжёлой инфраструктуры.
- Если тема продолжает ранее изученную, связывай её с уже знакомым материалом и предлагай короткий практический «вход» в задачу.
- Сохраняй оригинальные мысли, корректные объяснения и существующие требования проекта при редактировании; не переписывай страницы без необходимости.
- Следуй правилам `README.md` относительно `docs/`, frontmatter, русского языка, генерации метаданных и проверок.

## Структура учебных разделов

- Перед созданием новой страницы ищи материал по теме во всём `docs/`. Не создавай дубликат, если достаточно расширить или связать существующую страницу.
- Короткое определение или узкую тему оставляй одной страницей.
- Большую тему разбивай на папку с общей страницей `index.md` и отдельными подтемами. На обзорной странице указывай рекомендуемый порядок изучения и ссылки на все части.
- При преобразовании одиночной страницы в папку сохраняй понятный публичный маршрут, обновляй все внутренние ссылки и используй завершающий `/` для маршрута обзорного `index.md`.
- Если страница приближается к 1500 словам, проверь, не лучше ли разделить её: генератор исключает слишком большие страницы из локального поискового индекса через `search: false`.
- Внутри одной папки располагай темы от базовых понятий к практическому применению. Практику и задачи размещай после необходимой теории.

## Формат объяснений и примеров

- Пиши простым русским языком. Новый термин сначала объясняй обычными словами, затем показывай точное техническое название.
- Пример должен быть небольшим и воспроизводимым. Если используется внешняя зависимость, явно указывай её.
- Если в примере вызывается `print()`, рядом в комментарии показывай ожидаемый вывод. Для многострочного результата используй отдельный блок `text`.
- Разбирай важный код построчно: что получает каждая переменная, когда выполняется блок и что возвращается.
- Явно отделяй упрощённую учебную модель от точного поведения Python, ограничений и пограничных случаев.
- Не утверждай, что инструмент работает «с любым объектом», «всегда» или «без ограничений», если существуют значимые исключения.

## Задачи и самостоятельная практика

- Если пользователь просит только подсказки, не раскрывай готовое решение. Давай подсказки постепенно и указывай подходящие локальные страницы документации.
- Для задач в документации сначала перечисляй затрагиваемые темы, затем условие и подсказки.
- Полное решение размещай после подсказок в скрытом блоке `::: details Показать решение`.
- В решении объясняй не только код, но и причину выбора подхода. Добавляй типичные неправильные варианты, если они помогают понять тему.
- Для подходящей темы предлагай 1–3 задачи от простой к более сложной, не перегружая справочные страницы.

## VitePress и навигация

- Не редактируй `.vitepress/sidebar.generated.ts` и `.vitepress/theme/generated/content-index.ts` вручную. Они создаются командами проекта.
- Названия, порядок страниц и групп настраивай в `scripts/generate-sidebar.mjs` через существующие overrides.
- Делай подписи бокового меню короткими и осмысленными, обычно не длиннее трёх слов. После генерации проверяй, что автоматическое сокращение не создало фразы вроде «Типы значения и».
- Для папки с `index.md` добавляй отдельное название группы, порядок группы, название обзорной страницы и порядок вложенных страниц.
- После изменения маршрутов проверяй активный пункт меню, раскрытие нужной группы после перезагрузки и отсутствие старых ссылок.
- После завершения документации давай пользователю ссылку вида `http://localhost:5173/ml-interview/<route>` и, если локальный сервер запущен, проверяй ответ `200 OK`.

## Рабочий цикл проверки

После существенного изменения документации выполняй:

```bash
yarn sync:meta
yarn validate-content
yarn lint:md
yarn validate-links
yarn validate-routes
yarn type-check
yarn build
```

- После `sync:meta` просматривай сгенерированный sidebar для изменённого раздела.
- Проверяй примеры Python, если в них есть нетривиальная логика или ожидаемый результат не очевиден.
- Не добавляй отдельные тесты без запроса пользователя, но всегда запускай существующие проверки, соразмерные изменению.
- Если `git diff --check` сообщает об ошибке в несвязанном пользовательском файле, не исправляй его автоматически; явно отдели этот результат от своих изменений.

## Работа с существующими изменениями

- Рабочее дерево может содержать изменения пользователя. Не откатывай, не форматируй и не включай в свою работу несвязанные файлы.
- При пересечении с изменённым пользователем файлом сначала прочитай diff и встраивай изменение без потери существующей работы.
- При вопросе «есть ли эта информация» сначала выполни поиск по проекту. Если информация отсутствует или раскрыта только частично, добавь её в наиболее подходящий существующий раздел либо создай отдельную страницу при достаточном объёме.

## Git и публикация

- Веди счётчик файлов, изменённых Codex после последнего успешного push. Учитывай только файлы, относящиеся к выполненным задачам Codex; не учитывай и не включай несвязанные изменения пользователя.
- Когда счётчик достигает 10 изменённых файлов, обязательно выполни проверки, создай commit и отправь его напрямую в `origin/main`. После успешного push обнули счётчик.
- Сгенерированные файлы учитывай, если они изменились в результате текущей задачи и должны публиковаться вместе с исходными файлами.
- Формулируй commit message самостоятельно по фактическому содержанию изменений. Отдельное согласование текста commit message и дополнительное подтверждение push для этого порогового правила не требуются: этот пункт является постоянным разрешением пользователя.
- Перед автоматическим commit и push проверь `git status`, текущую ветку, upstream и фактическое назначение push. Добавляй в commit только относящиеся к задачам файлы.
- Не выполняй push, если обязательные проверки не прошли, текущая ветка не `main`, удалённая ветка содержит неизвестные изменения или невозможно безопасно отделить изменения пользователя. В этом случае сообщи конкретную причину остановки.
- Не создавай merge request без отдельного запроса.
- После каждого push проверяй статус CI/deploy и доступность опубликованного результата.

**Критерий готовности:** читатель может объяснить идею своими словами, воспроизвести пример и решить хотя бы одну небольшую вариацию задачи без копирования готового решения.
